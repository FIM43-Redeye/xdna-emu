# Firmware MMU Gaps

Xtensa MMU-v3 fidelity gaps in the M2b management-firmware interpreter (TLB
lookup, autorefill page-table walk, privilege/permission faults, double-fault
routing). Ground truth throughout M2b has been QEMU's Xtensa target as the ISA
reference; real-firmware behavior (traced instruction-by-instruction) is the
final oracle where the two could disagree.

| Gap | Model vs hardware | Where | Status / rationale |
|-----|-------------------|-------|--------------------|
| Double-exception DEPC / RFDE | QEMU (`exc_helper.c` `HELPER(exception_cause)`) writes `sregs[DEPC]` on a double exception (PS.EXCM already set) when `config->ndepc` is set; `translate_rfde` returns to DEPC without clearing EXCM. The pinned Phoenix firmware independently uses SR 0xC0 and ends its handler with `rfde`. | `src/firmware/xtensa/interp/mod.rs`, `decode/control.rs`, `interp/control.rs` | **Fixed 2026-07-26.** Double entry preserves EPC1, saves the faulting PC in DEPC, and vectors to the image-derived handler at VECBASE+0x278; `rfde` resumes at DEPC while leaving the outer handler in exception mode. |
| EXCVADDR not set on successful autorefill | QEMU sets `sregs[EXCVADDR] = vaddr` on a successful autorefill (`mmu_helper.c:831`), even though no fault is raised. This model omits it. | `src/firmware/xtensa/mmu.rs` (`Mmu::translate_inner`, the refill arm) | **Deliberate, unobservable here.** A successful refill enters no exception handler, and EXCVADDR is only ever read from a fault handler, so the omission has no observable effect in this model. |
| varway56 (ways 5/6 fixed vs software-writable) | Model defaults `varway56=false`: MMU ways 5/6 are two hard-wired region-protection entries per way, and `witlb`/`wdtlb`/`iitlb`/`idtlb` targeting them are silent no-ops. Real firmware's own boot prologue issues exactly these calls (AS bits 0-2 = 5 for `witlb`/`wdtlb`, AS bits = 6 for seven `iitlb`/`idtlb` calls) -- confirmed by stepping it. **Open question:** if the real AMD core configures `varway56=true`, those calls install the firmware's own high-region map, which this model cannot represent under the current default at all. | `src/firmware/xtensa/mmu.rs` (`Mmu::new`, `ways_5_and_6_hold_fixed_region_entries`) | **Coherence-inferred; M2c Task 1 (2026-07-04) searched for a literal config artifact and found none, but strengthened the evidence.** No AMD-authored `core-isa.h`, ConfigID, or Tensilica config string exists in the firmware image, `xdna-driver`, RyzenAI-SW, or the `$PS1` container header -- see [`2026-07-04-m2c-xtensa-config.md`](../superpowers/findings/2026-07-04-m2c-xtensa-config.md) for the full per-source search. That task's QEMU-core cross-reference *corrects* an earlier wrong assumption (that all six MMU-enabled QEMU reference cores agree on `varway56=false` -- they don't; it's a 3-3 split) and shows the one QEMU core sharing AMD's confirmed hardware generation (`de233_fpu`, Xtensa **LX7**.1.3) has `varway56=true`, consistent with every newer-generation core surveyed. Combined with the M2b boot-prologue coherence evidence (16 `witlb`/`wdtlb`/`iitlb`/`idtlb` calls at ways 5/6 that are meaningless no-ops under `false`), `varway56=true` now rests on two independent lines of evidence rather than one, with the **M2c Phase 1 coherence gate** (`docs/superpowers/specs/2026-07-04-m2c-mapping-boot-to-idle-design.md`) as the actual confirming mechanism. See [`2026-07-04-m2b-autorefill-characterization.md`](../superpowers/findings/2026-07-04-m2b-autorefill-characterization.md) for the original boot-trace evidence. |
| Spanning way 6 yields to every non-spanning way | QEMU `xtensa_tlb_lookup` treats all ways uniformly: any two hits are a multi-hit. This model treats configured spanning way 6 as the fallback; a hit in any non-spanning way shadows it, while two non-spanning hits still fault. | `src/firmware/xtensa/mmu.rs` (`Mmu::lookup`) | **Deliberate deviation, firmware-driven.** Two independent real-firmware paths leave the covering way-6 entry live: boot installs a paged mapping for `0x08b00000`, and context restore installs the exact way-5 mapping `0x10000000 -> 0x88000000`. Both then access the shadowing mapping without fault. The second path was observed while processing command 88 of the pinned Phoenix validation PDI during direct `EXEC_DPU` bring-up (2026-07-29). |
