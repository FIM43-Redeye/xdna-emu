# Handler `0x5948` static trace

Date: 2026-07-11  
Target: Phoenix/NPU1 `1502_00/npu.dev.sbin`  
SHA-256: `d13ff9fb95c6cea40213fa69e5a3465529f00bb67c0984d62343c6e31808fb9e`

## Verdict: NO

Handler `0x5948` does not write `FW_ALIVE_OFF` (`0x030bf000`). It is an
interrupt-controller/MERT event wrapper: it looks up per-channel metadata,
services the selected MERT object, acknowledges controller source `arg+0x20`,
clears Xtensa aggregate interrupt bit 0, and re-enables that controller source.

The overlay-correct recursive trace covers 1,099 reachable instructions, 38
direct calls, 10 indirect-call sites, and 100 store instructions with zero
decode walls. Nine indirect calls resolve from AT literals or the naturally
initialized scheduler state. The only unresolved target is the conditional
`callx8 a5` at `0x283b`, in the conservative context-switch expansion from
`0xd0b3 -> 0x2630`; its register is a data-dependent scheduler callback. That
arm is not taken in the captured go-alive state (`0xc86c` returns zero), and no
store on the feasible handler/MERT/controller path targets the SRAM band. Thus
the verdict is NO for sources `0x2d`/`0x2e` in the state that armed them, not a
claim that corrupted scheduler function pointers can never redirect execution.

There is no literal `0x030bf000` in the image. More importantly, every fixed or
initialized store base on the feasible path resolves outside
`0x030b0000..0x030c0000`.

## Framing and decoded entry

`0x5948` is AT-framed: file `0x5a48` (`vaddr+0x100`) begins with
`36 41 00`, decoded as `entry a1,32`. The BASE view at file `0x59a4`
does not begin with an `entry`. The apparent downstream wall at `0xd034` was
also a framing issue: AT file `0xd134` begins with a valid `entry a1,32`;
BASE bytes decode as unrelated instructions.

The complete handler body is:

```text
0x5948  entry a1,32
0x594b  l32r  a3,[0x32ec]          ; AT literal = 0x0000f260
0x594e  addx8 a3,a2,a3             ; record = 0xf260 + arg*8
0x5951  l8ui  a4,[a3+0]
0x5954  l32i.n a3,[a3+4]
0x5956  call8 0xc86c               ; scheduler-state predicate
0x5959  mov.n a12,a10              ; third argument = predicate result
0x595b  mov.n a10,a4               ; first argument = record byte
0x595d  mov.n a11,a3               ; second argument = record word
0x595f  call8 0xd034               ; service/post MERT event
0x5962  addi a2,a2,32              ; controller source = arg+0x20
0x5965  mov.n a10,a2
0x5967  call8 0x874c               ; acknowledge source and CPU aggregate
0x596a  mov.n a10,a2
0x596c  call8 0x86f8               ; re-enable controller source
0x596f  retw.n
```

For handler arguments `0x0d` and `0x0e`, the raw BASE metadata records at
`0xf2c8` and `0xf2d0` decode as `(byte 0, word 0x270ed004)` and
`(byte 8, word 0)`. The naturally booted emulator state has both records zero;
no natural pre-wait store initializes them. This agrees with the earlier
source-record trace and is another reason these sources are controller service
channels, not a hidden alive-publish selector.

## Call graph and indirect-edge bound

The feasible top-level graph is:

```text
0x5948
├── 0xc86c                 read scheduler/current-object state; no stores
├── 0xd034                 service one MERT object
│   ├── 0xc894             pending-event predicate; no memory stores
│   └── callx 0x588c       [0x1186c+0x24] in natural state
│       └── seven fixed internal event-byte stores, then return for arg=1
├── 0x874c                 controller acknowledge + wsr INTCLEAR,1
└── 0x86f8                 controller source-mask re-enable
```

`0xd034` has an additional conditional `0xd0b3 -> 0x2630` scheduler
context-switch arm. The recursive probe conservatively follows it. Its indirect
targets resolve as follows in the natural initialized state:

| call site | source | target |
|---:|---|---:|
| `0x273e` | `[[AT 0x255c]=0x1186c + 0x20]` | `0x5858` |
| `0x2809` | AT literal `0x2560` | `0x08b0e290` (`memset`) |
| `0xc4b8` | AT literal `0x3424` | `0x08b0e710` (cache maintenance) |
| `0xaf5c` | AT literal `0x31e4` | `0x08b0e290` (`memset`) |
| `0xca80`, `0xcada`, `0xceec` | `[[AT 0x3c90]=0x11868]` | `0x7c20` |
| `0xd081`, `0xd79e` | `[0x1186c+0x24]=[0x11890]` | `0x588c` |
| `0x283b` | conditional scheduler object callback | data-dependent |

The unresolved `0x283b` edge is bounded to the scheduler context-switch arm:
it is not called directly by `0x5948`, is reached only after `0xd0b3 -> 0x2630`,
and is guarded by a nonzero callback field loaded from the selected scheduler
object. The captured go-alive state makes `0xc86c` return zero, so `0xd034`
returns at its `beqz.n a4` rather than calling `0x2630`. The recursive expansion
nevertheless found no SRAM-band store in all direct callees reachable beyond
that conservative arm.

## Store destinations relevant to alive publication

### Fixed controller writes

`0x874c` loads AT literal `0x347c = 0x272003b0`, banks by
`(source >> 5)*4`, and writes the source bit at `0x8763`. `0x86f8` loads AT
literals `0x3474 = 0x116f0` and `0x3478 = 0x27200300`, updates the same bank,
and stores it at `0x871a` and `0x871c`.

| `0x0d` | `0x2d` | `0x871a s32i.n a2,[a3]` | `0x000116f4` | `old | 0x2000` |

aggregate Xtensa level-1 pending bit. These are interrupt acknowledge/mask
writes, not host-completion or SRAM writes.

### Resolved MERT event callback writes

The `0xd081` indirect call resolves to `0x588c`; it receives argument 1. AT
literals resolve its seven `s8i` destinations exactly:

```text
pc=0x58a4  [0x08a80678] <- 1
pc=0x58b3  [0x00027678] <- 1
pc=0x58b6  [0x00028678] <- 1
pc=0x58b9  [0x00029678] <- 1
pc=0x58bc  [0x0002a678] <- 1
pc=0x58bf  [0x0002b678] <- 1
pc=0x58c2  [0x0002c678] <- 1
```

For argument 1, `0x58c5 beqz.n a2` falls through to `0x58c7 retw.n`; the
conditional `0x58c9 -> 0x8770` call is not taken.

### Object and context-switch stores

`0xd034` stores only to fields of the selected MERT/scheduler object:

```text
0xd05d  [object+0x4c] <- 0
0xd065  [*(object+0x54)] <- argument word
0xd067  [object+0x58] <- 0
0xd06f  [object+0x2c] <- 1
0xd0a9  [object+0x50] <- updated event mask
```

The conservatively expanded context-switch graph stores to stack frames and
fields of objects rooted at the low scheduler tables `0x2250`/`0x11868`.
Its two resolved `memset` calls clear `0x2250..0x2273` and an 80-byte local
stack buffer. Neither is in the device SRAM band. No direct, literal-based, or
naturally initialized store base resolves to `0x030bf000` or anywhere in
`0x030b0000..0x030c0000`.

## Driver-side stimulus after `PSP_START_COPY_FW`

The driver does not issue an NPU interrupt/controller stimulus after
`PSP_START_COPY_FW` and before waiting for alive. `aie2_psp_start()` submits the
PSP start/copy command; `psp_exec()` toggles the PSP command-interface interrupt
register (`0`, then `1`) and polls the PSP status register until ready. After
that function returns, `aie2_hw_start()` immediately calls
`aie2_mgmt_chann_init()`, whose first substantive action is polling
`FW_ALIVE_OFF`. Mailbox creation and firmware-init messages happen only after
the alive pointer has been read.

Therefore the open-source driver does not identify a host write that raises
controller source `0x2d` or `0x2e` during this window. If either source is
asserted on silicon here, its physical stimulus is internal to PSP/NPU hardware,
not an explicit post-start driver doorbell. Source identity remains unresolved.

## Remaining mechanism ranking

Eliminating `0x5948` weakens the interrupt-publish theory. The evidence now
favors a PA-0 bus alias/side effect: the natural firmware deliberately writes
the exact silicon-observed pointer `0x030bb000` bytewise to PA `0..3`, while no
interrupt writer exists. A PSP load-time patch remains plausible because PSP is
the last external actor before the driver polls alive, but there is no patch
record in the flat image. Code past the `0x8cb1` frontier is least favored: the
local publish is already complete before that frontier and the driver performs
no later kick that would explain a delayed publication.

## Reproduction

The additive-only probe is `m2c_probe_handler_5948_trace` in
`src/firmware/boot_tests/static_tools.rs`:

```text
XDNA_FW_PROBE=1 XDNA_FW_MAX=100000 cargo test --lib \
  m2c_probe_handler_5948_trace -- --nocapture
```

It decodes raw BASE/AT bytes, recursively walks direct CFG edges, resolves
literal/initialized indirect targets, records every reachable store opcode,
and asserts that the image contains no `0x030bf000` literal and the resolved
store bases stay outside the SRAM band. It does not execute `0x5948`, deliver
an interrupt, or modify production `load_m2c`, scheduler, MMU, or interrupt
code.
