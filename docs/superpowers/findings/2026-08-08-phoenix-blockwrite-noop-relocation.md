# Phoenix BlockWrite NOOP Relocation

## Verdict

Relative CDO-record history is a causal input to Phoenix signed-firmware
`BlockWrite(1)` timing. At fixed target phase 44, fixed target byte offset and
record ordinal, fixed phase-40 predecessor, fixed payload, and fixed total
transaction size, moving one sixteen-record CDO `NOOP` block from before the
predecessor to immediately before the target changed the target cost by exactly
16 shim timestamp cycles:

| Arm | Sixteen-NOOP placement | Phase 40 | Phase 44 |
|---|---|---:|---:|
| control A | before phase-40 window | 246 | 232 |
| treatment B | between phase-40 and phase-44 windows | 246 | 248 |

The physical order A, B, A, B repeated digit-for-digit. The phase-40 witness
was 246 cycles in all four runs, so the treatment did not change the measured
predecessor window. The fail-closed classifier returned qualified
`history_sensitive` with a signed target delta of `+16` cycles.

This proves an ordering/recency effect across transaction records. It does not
identify whether the retained state belongs to firmware, a transaction engine,
MMIO, NoC, or another microarchitectural component. The numerical equality
between sixteen moved records and sixteen added target cycles is one treatment
point, not a one-cycle-per-`NOOP` law. No scheduler or timing cost is licensed
from this result alone.

All four candidate runs reproduced the expected output, retained the reported
low-QoS `400/800 MHz` identity before and after dispatch, included both shim
DMA lifecycle witnesses, and exposed exactly two alternating measurement
pairs:

| Ordinal | Arm | Marker timestamps | Intervals |
|---:|---|---|---|
| 1 | control A | `361169,361415,361535,361767` | `246,232` |
| 2 | treatment B | `359343,359589,360757,361005` | `246,248` |

| 4 | treatment B | `365045,365291,366459,366707` | `246,248` |

The raw gaps between windows differ because that is where the sixteen `NOOP`s
were deliberately relocated. They are outside both measured `BlockWrite`
windows and are not used as target costs.

The `finally` path ran the ordinary source transaction without QoS, reproduced
the expected output, restored the original reported default `600/1028 MHz`
identity, and left `/dev/accel/accel0` unowned. The recent kernel query showed
no NPU, amdxdna, or DRM warning/error. The unrelated existing ACPI debug line
was preserved in the receipt.

## Licensed conclusions

This evidence licenses only the following:

1. A phase/payload/ordinal-only `BlockWrite(1)` cost is falsified for this
   pinned Phoenix tuple.
2. The relative placement of a sixteen-record CDO `NOOP` block and the fixed
   phase-40 predecessor causally changes the phase-44 target by 16 shim cycles.
3. Any eventual timing model needs transaction-history state across record
   boundaries. The current signed-firmware interpreter follows the same 47-PC
   path in both arms, so a stateless per-record emulator cost cannot reproduce
   both physical target costs.
4. The observation does not distinguish recent-`NOOP` state from elapsed
   distance since the predecessor, nor identify the physical state carrier.
5. Do not infer a marginal cost, fit a delay, begin payload scaling, or change
   the scheduler from this single full-turn treatment.

The next boundary is a separately reviewed history-depth/count discriminator
that preserves the same fail-closed balance. Older firmware, AIE2P, live clock
phase, and a production management-processor timing model remain open.
