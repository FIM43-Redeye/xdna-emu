# AGENTS.md

Repository guidance for coding agents: what the code can't tell you.
Reference material lives one hop away under `docs/`.

**Derive from the toolchain.** The open-source toolchain (aie-rt, llvm-aie,
mlir-aie) is the specification for hardware behavior; the real NPU is ground
truth. Never hardcode what can be extracted. See "Sources of truth" below.

## Workspace

Work from the parent `npu-work` directory, not from xdna-emu: the workspace
loads the NPU environment (mlir-aie, Peano, aietools, XRT, the
`ironenv` venv) and holds the sibling repos:

- `aie-rt/driver/src/` - official Xilinx aie-rt (HAL): register defs and the
  DMA/lock/stream-switch implementations. Not mlir-aie's vendored fork.
- `mlir-aie/` - compiler, test suite, device models;
  `lib/Dialect/AIE/Util/aie_registers_aie2.json` is the AM025 register database.
- `llvm-aie/` - Peano (LLVM with the AIE backend, TableGen ISA definitions).
- `xdna-driver/` - Linux kernel driver and user-space shim.

Toolchain paths resolve from `MLIR_AIE_PATH` / `LLVM_AIE_PATH` / `AIE_RT_PATH`
(which names `driver/src`), then `NPU_WORK_DIR`, then ancestor discovery;
explicit paths fail closed. `tblgen-rs` uses the host LLVM 21, not Peano
(`TABLEGEN_210_PREFIX` overrides). The compiler driver is the C++ `aiecc`;
anything still calling `aiecc.py` (removed upstream July 2026) is stale.

Recovery procedures and operational detail: [`docs/operations.md`](docs/operations.md).
Status: [ROADMAP.md](ROADMAP.md) and `docs/roadmap/`; run `cargo test --lib` for
the current test count, since numbers written in docs go stale.

## Sources of truth

In priority order (what each provides and where the emulator consumes it:
[`docs/toolchain-sources.md`](docs/toolchain-sources.md)):

1. **aie-rt** (branch `xlnx_rel_v2026.2`): the HAL that programs real silicon;
   the reference for DMA, lock, and stream-switch behavior. If aie-rt does it a
   particular way, so do we.
2. **AM025 register database**, parsed by `regdb.rs`. BD parsing is fully
   data-driven from it (no hardcoded bit positions in `bd.rs`); extend that.
3. **llvm-aie TableGen** (`llvm/lib/Target/AIE/`): the ISA. Decoding is fully
   TableGen-driven; semantics are partly data-driven via SemanticOp, and closing
   that gap is the goal.
4. **mlir-aie device model** (`tools/aie-device-models.json`, regenerated by
   `tools/mlir-aie-bridge.py device-model`): array topology.
5. **Hardware observation** on the real NPU, which settles any disagreement.
6. **AM020/AM025** manuals, only for what the above don't cover (mainly vector
   compute semantics, stream-switch port types, micro-timing).

These sources are large: navigate with targeted searches and narrow reads.

## Target facts the code doesn't spell out

- NPU1 (Phoenix/Hawk Point, AIE2) is the primary target; AIE2P parts (Strix,
  Strix Halo, Krackan) are planned; Versal is out of scope.
- Phoenix has 29 tiles: `(0,0)` is absent, column 0 rows 1-5 are DPU-reserved,
  and application columns start at physical column 1.
- mlir-aie device names differ from driver IDs: `npu1*` -> NPU1, `npu2*` -> NPU4
  (Strix). NPU2/NPU3 are deprecated prototypes.

## Build and test

```bash
cargo build [--release]
cargo run -- <subcommand> ...                    # bare `xdna-emu` opens the GUI
./scripts/run-tests.sh [--lib]                   # all tests / library only
./scripts/emu-bridge-test.sh                     # bridge suite (needs XRT + NPU)
./scripts/emu-bridge-test.sh --no-hw add_one     # quick EMU-only
cargo build -p xdna-emu-ffi                      # rebuild the FFI .so
./scripts/rebuild-plugin.sh [--release]          # full plugin build + install
```

- **The FFI `.so` is a separate crate.** `libxdna_emu.so` is the
  `xdna-emu-ffi` cdylib; workspace `cargo build` and `cargo test --lib` do not
  rebuild it. `emu-bridge-test.sh` and `isa-test.sh` do; direct `.so` or plugin
  use needs `cargo build -p xdna-emu-ffi`. A stale `.so` causes phantom bugs.
- Don't run the same cargo invocation twice concurrently (debug and release
  together are fine).
- **Bridge tests are the real validation target**: `test.exe -> XRT -> plugin
  -> emulator`. Every test compiles with both compilers; Chess is ground truth,
  Peano failures are informational. Results land in
  `build/bridge-test-results/YYYYMMDD/` (symlink `latest`); `--help` lists the
  flags. `src/testing/xclbin_suite.rs` runs xclbins in-process without XRT.
- **Differential fuzzers** (`xdna-emu fuzz`, `fuzz-vector`, `fuzz-dma`; `--hw`
  runs the differential, `fuzz-vector --replay <dir>` diffs against a banked
  silicon corpus).
- **Tracing**: upstream mlir-aie owns trace injection and decoding; we own the
  prep, sweep, matrix, and regression-verification layer, which is the
  regression gate for emulator work. Keep it until upstream ships an
  equivalent. See [`docs/trace/strategy.md`](docs/trace/strategy.md).
- **Memory watch**: `XDNA_EMU_WATCH=addr:bytes,...` (hex) with `RUST_LOG=info`
  logs every access, cycle-correlated (grep `[WATCH]`). DMA watches use
  tile-local offsets; core watches the 20-bit space (0x70400 = local 0x400).
- Append aietools to `LD_LIBRARY_PATH`, never prepend it.

## XRT plugin (`xrt-plugin/`)

XRT loads the plugin `.so` in place of the real XDNA driver; it delegates to the
emulator through `crates/xdna-emu-ffi/`. It compiles SHIM sources from the
sibling `xdna-driver-xrt-2.26` worktree (branch `emu-shim-xrt-2.26`, which pins
`xrt` to `emu-xrt-2.26`, the XRT installed in `/opt`). The main `xdna-driver`
checkout stays on `emu-shim-base` and is not a plugin source;
`rebuild-plugin.sh` warns on the wrong branch (`XDNA_DRIVER_DIR` overrides).

- `XDNA_EMU` (any value) makes the plugin replace `xrt::device(0)`; unset means
  real hardware. For HW runs from such a shell: `env -u XDNA_EMU ...`.
- `XDNA_EMU_RUNTIME=release|debug` picks the `.so` profile (default `debug`).

## Working rules

- **Finish what you start.** Bring an isolated subsystem (control packets, DMA
  padding, cascade flows, ...) to 100% before moving on: every case passes on
  both compilers and on both HW and EMU. Half-done features make "not done yet"
  indistinguishable from a real bug.
- **Match real hardware**, not a simplified approximation. From a failing test,
  work backward from the failing assertion through the data path; if hardware
  semantics are unclear, ask rather than guess.
- **Correctness before performance.** No optimization (including
  multithreading) until behavior is indistinguishable from hardware.
- **Validate every change** with `cargo test --lib`; a newly failing test is a
  regression to fix first.
- **HW is the cheap oracle; EMU is the slow part.** A targeted HW capture costs
  microseconds, so err toward HW runs when they can settle a question.
  `isa-test.sh` takes ~5-10 min and `emu-bridge-test.sh` ~15-30 min: run the
  full suites once after a batch of fixes, not to check progress.

## Operations

Full procedures (recovery chain, SMU command map, environment state):
[`docs/operations.md`](docs/operations.md).

- **Never run two hardware suites concurrently**; bridge and ISA tests both grab
  the NPU. `cargo test --lib` is safe alongside.
- **No persistent work in `/tmp`.** Tools go under `tools/` or `scripts/`,
  experiment output under `build/experiments/` (gitignored, the only copy of HW
  evidence: rescue it before removing a worktree).
- **Privileged operations** (module reloads, DKMS installs, reboots) need the
  machine owner's authorization; how that works is machine-specific. Never
  reboot the machine unasked.
- **When the NPU wedges**, reload the driver
  (`modprobe -r amdxdna && modprobe amdxdna`) first. If processes are stuck in D
  state, capture state to `build/experiments/` and reboot instead.
